# Compaction Manifest and Job Contract — v0.1

**Status:** M3 prototype implementation contract  
**Scope:** Immutable compaction inputs, candidate outputs, job lifecycle and safety invariants  
**Runtime status:** CIM1/OWM1/PVM1 codecs, source preflight, bounded candidate execution, three layout strategies, AWP1 generation promotion/rollback and startup reconciliation are implemented. See the M3 research report and per-run CI benchmark artifact for measurement methodology and evidence.

## 1. Purpose and boundary

M2 established immutable Chronicle ingestion records, derived Capsules and a correctness-first Navigation Map. M3 introduces offline physical reorganisation without changing the logical table or weakening the source of truth.

A compaction attempt consumes a pinned set of verified Capsule generations and writes a new, independently verifiable candidate Weave generation. It never edits a Chronicle record or Capsule in place. It never makes a candidate active. Active-generation publication, rollback and source reclamation belong to M3.3 or later.

The first implementation is explicit and offline. There is no scheduler, background compaction, automatic layout selection, concurrent-writer guarantee or Chronicle reclamation in this contract.

## 2. Stable identities

A compaction attempt is identified by:

- **TableId:** the stable catalog table identity;
- **JobId:** a nonzero 128-bit job identity generated by ANANTA;
- **Attempt:** a nonzero, monotonically increasing attempt number within the job.

A source Capsule is pinned by the tuple:

**(TableId, CapsuleId, CapsuleGeneration, FileLength, FileSHA256)**

The source sequence interval, row count and schema revision are copied into the manifest as validation fields. A Capsule ID/generation without its exact file fingerprint is not a sufficient source reference.

A source Chronicle batch is pinned by:

**(TableId, IngestionSequence, BatchId, PayloadSHA256, RowCount, RecordFileLength, RecordFileSHA256)**

This receipt inventory makes the expected logical source coverage explicit. The Chronicle record remains authoritative and is re-verified when the attempt validates its inputs.

A candidate Weave is identified by **(TableId, WeaveId, Generation)**. Candidate identity is immutable and cannot overwrite an existing generation.

## 3. Input manifest

The input manifest is an immutable snapshot of the exact data selected for one attempt. It contains:

- format version, TableId, JobId and Attempt;
- target schema revision captured when the job is planned;
- inclusive source coverage [first_sequence, last_sequence];
- expected total row count;
- ordered Capsule references, each with identity, generation, schema revision, sequence interval, row count, byte length and SHA-256 file fingerprint;
- ordered Chronicle receipt references for every sequence in the coverage interval;
- aggregate input-manifest SHA-256 over its canonical serialized representation.

The manifest must satisfy all of these conditions before compaction starts:

1. Every Capsule belongs to the same TableId and has a canonical path under that table's capsules directory.
2. Every referenced Capsule exists, has the recorded length and fingerprint, and passes the independent Capsule validator.
3. Capsule source intervals are sorted, non-overlapping and exactly tile the declared coverage interval. A gap, overlap or repeated Capsule identity rejects the manifest.
4. The Chronicle receipt inventory contains exactly one verified receipt for every sequence in that interval. Its BatchId and payload fingerprint must match the durable Chronicle record.
5. For each Capsule interval, the sum of Chronicle receipt row counts equals the Capsule row count. The sum across all inputs equals the manifest total.
6. Capsule rows have a defined logical origin order: ingestion sequence ascending, then row ordinal ascending within each committed Chronicle batch. This is the order produced by the current Capsule builder. Input validation must reconstruct that mapping from the verified Chronicle receipts and compare each decoded Capsule row against the corresponding Chronicle-derived row after target-schema resolution; row counts and min/max statistics alone are insufficient.
7. The target schema snapshot exists and is immutable. Historical source payloads are resolved to it by stable ColumnId; column names are not identity.
7. All path components are derived from validated numeric identities. A manifest cannot name an arbitrary path, parent directory, symlink target or file outside the table's data root.

The initial compaction input is deliberately a contiguous source interval. Sparse selection, partial-Capsule compaction and mixing legacy ANF segments with Chronicle-derived Capsules are out of scope until their lineage semantics are specified.

## 4. Output manifest and row provenance

An output manifest is immutable and is published only after all candidate files have been written, synced and independently verified. It contains:

- format version, TableId, JobId and Attempt;
- candidate WeaveId and Generation;
- exact input-manifest SHA-256;
- target schema revision and source coverage interval;
- layout profile (append-only, time-first or entity-first);
- expected total row count;
- one or more output artifact references, each with canonical relative path, byte length, SHA-256, row count and provenance-sidecar reference/fingerprint;
- aggregate output-manifest SHA-256.

The sum of output artifact row counts and provenance entry counts must equal the input row count. Every output row has a stable origin identity:

**(TableId, IngestionSequence, RowOrdinalWithinBatch)**

The origin identity is independent of physical row order. The output provenance sidecar maps each physical row to exactly one origin identity. Validation sorts or externally orders the fixed-width origin identities and proves exact set equality with the input receipt inventory expanded by each batch's row count. Duplicate origins, missing origins, unknown sequences, out-of-range row ordinals or repeated origins reject the candidate. For every origin, validation recomputes a canonical typed-row fingerprint from the decoded output values and compares it with the fingerprint derived from the corresponding verified Chronicle source row under the pinned target schema. This comparison uses the engine's canonical typed encoding (not language-level floating-point equality), so physical reordering cannot conceal altered values and NaN/signed-zero handling is deterministic. Row count and origin-set equality alone are not accepted as proof of logical equivalence.

The output manifest records the complete input lineage, not merely the minimum and maximum source sequence of each output file. A time-first or entity-first layout may place rows from distant source sequences in the same output file.

M3.1 defines this manifest contract; the candidate data-file and provenance-sidecar codecs are implemented with the M3.2 Weave strategies. Until then, no existing Capsule format is reinterpreted as a Weave.

## 5. Job state machine

The durable job journal is append-only. Each state event includes JobId, Attempt, monotonic event sequence, state, input-manifest fingerprint, progress counters when available, and a record checksum.

Allowed forward transitions:

**planned → validating_inputs → running → verifying → publishing → completed**

Cancellation transitions:

**validating_inputs | running | verifying → cancellation_requested → cancelled**

A nonterminal state may transition to failed when an invariant or I/O operation fails. A process interruption is recovered as interrupted for that attempt; it is not silently represented as success. Terminal states are completed, cancelled, failed and interrupted.

Progress is observational only. It is checkpointed at bounded work-unit boundaries and is never used as evidence that output is correct.

### CJE1 journal event record

The first runtime event codec uses a fixed 160-byte little-endian record:

| Offset | Length | Field |
|---:|---:|---|
| 0 | 4 | Magic: `CJE1` |
| 4 | 2 | Version: 1 |
| 6 | 1 | State code |
| 7 | 1 | Reserved zero |
| 8 | 16 | JobId |
| 24 | 8 | Attempt |
| 32 | 8 | Monotonic event sequence |
| 40 | 32 | Input-manifest SHA-256 |
| 72 | 56 | Seven u64 counters: input bytes, output bytes, temporary bytes, working-memory bytes, rows processed, open files and current work-unit rows |
| 128 | 32 | SHA-256 of bytes 0 through 127 |

State codes are Planned=0, ValidatingInputs=1, Running=2, Verifying=3, Publishing=4, CancellationRequested=5, Completed=6, Cancelled=7, Failed=8 and Interrupted=9. Unknown state codes, nonzero reserved bytes, zero identity fields, wrong lengths and checksum mismatches are rejected.

The current Rust implementation provides the event encoder/decoder, in-memory state reducer, durable append-only CJE1 journal file operations and full-file replay validation. Each per-attempt journal is capped at 64 MiB (419,430 complete events). Appends sync the journal file; first creation also syncs its parent directory on Unix. Partial tails, checksum damage, non-regular files and journals above 64 MiB are rejected without truncation. Startup recovery preserves corrupt/partial journals; for valid unfinished attempts it verifies any final candidate against its persisted CIM1/OWM1/PVM1 and appends Completed only if verification succeeds. Otherwise it appends Interrupted and removes only regular files in that attempt's canonical staging directory. Retries require a fresh Attempt.

Recovery rules:

- If a valid output manifest is durably present and all referenced outputs pass independent verification, recovery may reconcile a missing final journal event to completed.
- If publication did not commit, the attempt is interrupted or failed; its partial staging files are never readable as committed data.
- A retry uses a fresh Attempt and staging directory. It must pin the same input-manifest fingerprint unless the caller creates a new JobId.
- M3.1 chooses safely discardable attempts, not in-place resume. Resuming partial sort/compaction state is deferred until checkpoints have a separately specified integrity contract.

## 6. Temporary output and publication

All output is written beneath a job- and attempt-owned staging directory on the same filesystem as the final candidate generation. Temporary names are canonical and contain the JobId, Attempt and output ordinal.

Publication order:

1. Validate and pin all inputs.
2. Create staging files exclusively; never truncate or reuse a pre-existing path.
3. Write bounded chunks while enforcing resource budgets.
4. Flush and sync every completed data and provenance file.
5. Re-open and independently validate each staged output, including provenance coverage.
6. Publish each immutable output file with no-overwrite semantics.
7. Sync the containing directory where the platform supports it.
8. Publish the output manifest last, using same-directory temporary creation, file sync and no-overwrite atomic publication.
9. Record completed only after the output manifest is durable.

An output set without its valid output manifest is an incomplete candidate and must not be scanned or promoted. A post-publication error is treated as uncertain: inspect and verify the exact final path before retrying. Never overwrite to make a retry appear successful.

Cleanup may remove only regular files in the canonical staging path owned by the interrupted JobId/Attempt, and only after confirming that no live job owns the directory. Unknown files, symlinks, published outputs and source data are left untouched. Original Chronicle and Capsule inputs remain available after success, failure and cancellation.

## 7. Resource budgets

Every attempt snapshots finite limits before starting. The initial contract includes:

- maximum input bytes;
- maximum output bytes;
- maximum aggregate temporary bytes;
- maximum resident working memory;
- maximum rows;
- maximum simultaneously open files;
- maximum work-unit size used for cancellation/progress checkpoints.

All counters use checked arithmetic. Limits are enforced before allocation or write where possible and rechecked against actual bytes written. Temporary-space accounting covers all staging files for the attempt, not just one output file. Exceeding a budget fails the attempt without changing the source set or active database view.

Concrete defaults and public configuration names are selected during implementation after measurements; an unlimited or silently ignored limit is not permitted.

## 8. Cancellation

Cancellation is cooperative and checked before and after bounded read, decode, sort, write and verification work units. The maximum cancellation delay is bounded by one configured work unit plus the current filesystem operation; no hard real-time interruption is claimed.

Cancellation is accepted through the end of verifying. Once publishing begins, cancellation returns a too-late result: publication must either finish as a valid immutable candidate or be reconciled as interrupted. A cancellation request never deletes source data and never exposes a partial output manifest.

## 9. Concurrency and visibility

The first implementation runs under the existing exclusive local database-writer ownership. It snapshots source identities while that ownership is held and rejects stale input fingerprints before writing. This is not a multi-process compaction scheduler.

M3.1 candidate output is invisible to normal scans. M3.3 must introduce and test an active-generation manifest, atomic promotion, retention and rollback before any candidate can replace the read path.

## 10. M3.1 acceptance tests

The implementation is not complete until automated tests cover:

- missing, modified, truncated, duplicate, overlapping and non-contiguous input references;
- missing, duplicate and mismatched Chronicle receipts and row counts;
- schema evolution resolved by stable ColumnId;
- duplicate, missing, unknown and out-of-range row provenance;
- output checksum, length and manifest mismatch;
- pre-existing temp/final paths and no-overwrite publication;
- injected failure at every write, sync and publication boundary;
- interruption recovery and safe cleanup of only attempt-owned staging files;
- cancellation at each bounded work-unit boundary and the publishing boundary;
- memory, input, output, temporary-space, row and open-file budget exhaustion;
- source files and any existing active view remaining unchanged for every failure mode.

The M3.1 exit gate also requires all existing workspace tests, formatting, Clippy and native examples to pass.

## 11. Explicit non-goals

This contract does not implement a compaction scheduler, online ingestion during compaction, active-generation promotion, rollback, source reclamation, WAL, transactions, MVCC, AQL, query planning or production durability. It does not claim performance benefit. M3.2 must measure append-only, time-first and entity-first candidates on identical logical data; M3.3 owns generation promotion and rollback.


**Implementation note (2026-11-05):** The Rust workspace now contains the CIM1 encoder/decoder, SHA-256 fingerprint calculation and structural validation for contiguous Capsule and Chronicle inventories. This does not verify on-disk files; exact file preflight, output-manifest encoding, provenance verification and compaction execution remain separate M3.1 tasks.



## 13. Canonical Output Manifest Binary Format — OWM1

OWM1 describes one immutable, invisible candidate Weave generation. It does not promote the candidate or change the normal read path.

The record is:

**OWM1 | 136-byte fixed header | ordered artifact references | SHA-256 | OEND**

The SHA-256 covers the complete header and artifact-reference body. The four-byte OEND marker follows the digest. All integers are little-endian.

### Fixed header (136 bytes)

| Offset | Bytes | Field |
|---:|---:|---|
| 0 | 4 | Magic: OWM1 |
| 4 | 2 | Version: 1 |
| 6 | 2 | Flags: zero |
| 8 | 4 | Header length: 136 |
| 12 | 8 | TableId |
| 20 | 16 | JobId |
| 36 | 8 | Attempt |
| 44 | 8 | Candidate WeaveId |
| 52 | 8 | Candidate generation |
| 60 | 32 | Input CIM1 body SHA-256 fingerprint |
| 92 | 8 | Target schema revision |
| 100 | 8 | First source sequence |
| 108 | 8 | Last source sequence |
| 116 | 1 | Layout: 0 append-only, 1 time-first, 2 entity-first |
| 117 | 3 | Reserved zero |
| 120 | 8 | Expected total row count |
| 128 | 4 | Artifact count |
| 132 | 4 | Reserved zero |

### Artifact reference (104 bytes each)

| Offset | Bytes | Field |
|---:|---:|---|
| 0 | 4 | Zero-based artifact ordinal |
| 4 | 4 | Reserved zero |
| 8 | 8 | Data file byte length |
| 16 | 32 | SHA-256 of complete data file |
| 48 | 8 | Data row count |
| 56 | 8 | Provenance sidecar byte length |
| 64 | 32 | SHA-256 of complete provenance sidecar |
| 96 | 8 | Provenance entry count |

The artifact ordinal derives the canonical relative paths beneath the candidate generation: data-NNNNNNNN.wvf and provenance-NNNNNNNN.pvm. Paths are not accepted from the manifest, preventing traversal and arbitrary file selection.

### Canonical constraints

- The total encoded record is limited to 64 MiB and 250,000 artifacts.
- TableId, JobId, Attempt, WeaveId, generation, input fingerprint, target schema revision, source sequence interval and expected row count are nonzero/valid.
- Artifact ordinals are contiguous and ordered from zero. Every data and provenance file has a nonzero length and nonzero SHA-256.
- Each artifact has a positive row count and exactly the same provenance-entry count. The checked sum of artifact row counts equals ExpectedRowCount.
- Unknown layout values, nonzero flags/reserved fields, invalid lengths, count/length mismatch, checksum mismatch and trailing bytes are rejected.
- OWM1 does not prove that a provenance sidecar contains the correct origins. Before publication the worker must independently verify each file's length and SHA-256, decode every sidecar entry, and prove exact set equality with the input receipt inventory expanded by row ordinal. It must also decode output rows and validate their canonical typed-row fingerprints.
- Candidate output remains invisible until M3.3 implements active-generation promotion and rollback.

The OWM1 codec validates the immutable output inventory, not the physical Weave data format. Data and provenance codecs are implemented with M3.2 layout strategies.


## 14. Database Source Preflight

The database source-preflight API accepts a decoded CIM1 manifest and checks that its TableId and target schema revision still match the open database. It resolves Chronicle receipt references through the table's reconstructed receipt index and requires canonical table-local segment record filenames. Capsule paths are derived from the numeric CapsuleId and generation under the table capsules directory.

Before a source is accepted, the preflight checks each parent directory is a real directory (not a symlink), each source is a regular non-symlink file, the exact byte length and complete-file SHA-256 match CIM1, and the embedded format validator accepts the Chronicle or Capsule record. Capsule validation also recomputes ANF column statistics and temporal bounds and verifies ColumnId-based resolution into the target schema. No source is modified, renamed or deleted.

The preflight report returns verified Capsule and Chronicle-record counts, aggregate source bytes, total rows and the exact CIM1 body fingerprint. The bounded execution API consumes this report, rechecks the source snapshot immediately before reading rows, and writes a candidate without changing source files or normal scan visibility.



## 15. Runtime candidate execution — first prototype

The first bounded executor uses deterministic attempt-owned staging beneath the table's weaves directory. It snapshots and rechecks CIM1 preflight, enforces max_rows and a conservative input-derived working-memory estimate before allocating row vectors, and emits ANF-v2 data artifacts no larger than the configured work unit, 65,536 rows or the ANF decoded-cell limit. This prototype uses a finite in-memory working set rather than an external-sort spill engine: workloads whose estimate exceeds max_working_memory_bytes fail before execution. This is a finite prototype limit, not a claim of unlimited-scale external sorting.

Append-only preserves source sequence and row ordinal. Time-first sorts by the first TIMESTAMP_MICROS column. Entity-first sorts by the first UTF8/integer column. Sorted profiles sort bounded runs and perform a deterministic k-way merge with source origin as tie-breaker. Mixed layout is not implemented unless later workload evidence justifies it.

Each artifact has an ANF-v2 data object and a PVM1 sidecar. PVM1 stores IngestionSequence, RowOrdinal and TypedRowSHA256 per physical row. Candidate verification reopens every staged file, verifies its OWM1 length/hash, decodes the data and PVM1, and proves exact equality with the input origin/fingerprint inventory. OWM1 is written last; the complete staging directory is atomically renamed into the immutable candidate generation path. It remains inactive.

The executor journals Planned, ValidatingInputs, Running, Verifying, Publishing and Completed transitions in CJE1. Cancellation is checked at bounded row, sort-run and output-merge work-unit boundaries; once Publishing is journalled, cancellation is too late. Progress tracks input/output/temp bytes, estimated working memory, rows and open files. Execution reports record wall duration, Linux process CPU time when available, final candidate storage bytes, temporary disk amplification and candidate read/decode latency.

execute_compaction and verify_compaction_candidate do not modify source Chronicle/Capsule files or normal scan visibility. Each immutable candidate stores the exact input CIM1, OWM1 and data/provenance artifacts. AWP1 promotion is a separate operation that verifies the candidate and reference logical scan before changing active visibility.


## 16. Active generation pointer — AWP1

AWP1 is the atomic read-path selector stored in data/table/weaves/active.awp. It is a fixed 128-byte little-endian header followed by SHA-256 and AEND. It stores TableId, monotonic pointer revision, current WeaveId/generation and complete OWM1 SHA-256, plus the retained previous generation identity and OWM1 SHA-256. A previous generation is either entirely absent (all zero fields) or entirely present.

Promotion is allowed only when the candidate covers the complete Chronicle sequence range beginning at one and there are no legacy ANF segments outside the pinned inventory. The candidate is independently verified against CIM1 and PVM1, and its typed-row fingerprint multiset is compared with the current logical table scan before the pointer is switched. The pointer temp file is created exclusively in the same directory, fully written and synced, then renamed over active.awp; the directory is synced. No candidate data file is overwritten or deleted.

Normal row scans read the current active OWM1 and substitute its Weave data artifacts for the Chronicle records whose sequences are covered by that manifest. Chronicle records outside the active interval remain visible. The old generation is retained as the rollback target. Rollback is a new pointer revision that swaps current and previous identities; it never rewrites source data or deletes either generation.

On open, an active pointer is decoded and its current candidate is fully reverified from persisted CIM1, OWM1, data artifacts and PVM1 provenance. If the active candidate is missing or invalid and the retained previous generation verifies, recovery publishes a new pointer selecting the previous generation. If neither generation verifies, opening fails closed.

The atomic replace guarantee is validated on Unix filesystems with same-directory rename and directory sync. Platforms without equivalent atomic replacement must not claim crash-safe promotion until a platform-specific primitive is supplied.


## 17. M3.2 measurement methodology and conclusion

The reproducible CI example creates 10,000 telemetry rows in ten Chronicle batches, builds one Capsule per batch, and produces append-only, time-first and entity-first candidates from the same full-coverage CIM1 inventory. It records build wall time, Linux process CPU time when available, source/output/temp/final bytes, temporary disk amplification, artifact count and five warm candidate read/decode samples per layout. The workflow uploads the raw JSON as the chrono-weave-m3-benchmark artifact for each run.

The initial performance conclusion is intentionally conservative: the current full-table scan decodes every selected Weave artifact and does not exploit physical ordering for range pruning or query planning. Time-first/entity-first therefore do not reduce rows decoded in the current workload and add sorting/merge work. No performance benefit is claimed; append-only remains the default. This negative result is documented in docs/research/chrono-weave-m3-report.md. The mixed layout was evaluated against this workload and is not justified; it remains unimplemented.

Linux process CPU time is sampled from procfs and the system clock-tick rate. Non-Linux platforms return null; wall time is not presented as CPU time. The benchmark is a synthetic single-node prototype workload, not a production performance claim.


## 17. WAL publication boundary

The immutable candidate directory and OWM1 output manifest are now published under the M6.2 WAL protocol. The committed OWM1 intent identifies the complete staged candidate and recovery completes the stage-to-final directory rename before the CJE1 job journal is reconciled. This does not promote the candidate to active visibility; AWP1 promotion remains a separate WAL-backed operation.
